# Feature Rules: Internationalization & Localization (i18n / l10n)
> Loaded when: features.i18n=true

## The Core Distinction
- **i18n (engineering)** — externalize strings, support Unicode, format dates/numbers/currencies per locale, route per language. Done once in architecture.
- **l10n (content)** — actual translation, cultural adaptation, locale review. Done repeatedly per market.
- **Get i18n right first. l10n cannot fix bad i18n architecture.**

---

## Stack

```
i18next + react-i18next      ← translation engine
typesafe-i18n (types only)   ← compile-time key safety
i18next-cli                  ← static key extraction + CI validation
tailwindcss-rtl plugin       ← CSS logical properties for RTL
Intl API (built-in)          ← dates, numbers, currencies, units
Cloudflare cf.* headers      ← free locale/timezone detection at edge
```

## Rule 1 — Zero Hardcoded Strings

```typescript
// ✅ Always
const { t } = useTranslation('dashboard')
return <h1>{t('overview.title')}</h1>

// ❌ Never — even for "obvious" strings
return <h1>Overview</h1>
return <button>Save</button>
return <p>No results found</p>
```

**Every user-facing string goes through i18n. No exceptions. Ever.**
- Error messages: `t('errors.network_timeout')`
- Tooltips: `t('tooltips.export_button')`
- ARIA labels: `aria-label={t('a11y.close_modal')}`
- Email subjects: `t('emails.welcome.subject')`
- Toast messages: `t('toasts.saved_successfully')`
- Empty states: `t('empty.no_results')`

## Rule 2 — Type-Safe Translation Keys

```typescript
// types.ts — generated from en/ locale
import type { BaseTranslation } from 'typesafe-i18n'

export type Namespaces = 'common' | 'auth' | 'dashboard' | 'errors' | 'emails'

// i18next.d.ts — enables IntelliSense + compile-time checks
import 'i18next'
declare module 'i18next' {
  interface CustomTypeOptions {
    defaultNS: 'common'
    resources: {
      common: typeof import('./locales/en/common.json')
      auth: typeof import('./locales/en/auth.json')
      dashboard: typeof import('./locales/en/dashboard.json')
      errors: typeof import('./locales/en/errors.json')
    }
  }
}

// Result: typos in t() keys = TypeScript error at compile time
t('auth.login.titlee') // TS Error: Property 'titlee' does not exist
t('auth.login.title')  // ✅ Valid
```

**CI enforces:** `pnpm i18n:check` — runs i18next-cli static analysis, fails build on missing keys.

## Rule 3 — Key Naming Convention

```json
// ✅ Namespaced + dot-notation hierarchy
{
  "login": {
    "title": "Sign in to your account",
    "subtitle": "Welcome back",
    "form": {
      "email_label": "Email address",
      "email_placeholder": "you@example.com",
      "password_label": "Password",
      "submit": "Sign in"
    },
    "errors": {
      "invalid_credentials": "Invalid email or password",
      "account_locked": "Account locked. Try again in {{minutes}} minutes."
    }
  }
}

// ❌ Flat, ambiguous, unnamespaced
{
  "loginTitle": "Sign in",
  "emailLabel": "Email",
  "invalidCreds": "Wrong password"
}
```

**Rules:**
- Keys are `snake_case` — never camelCase in JSON
- Max 3 levels deep: `page.section.element`
- Interpolation: `{{variableName}}` — never string concatenation
- Pluralization: use i18next `_one` / `_other` / `_zero` suffixes
- Context variants: `button_loading`, `button_default` — never conditional strings in components

## Rule 4 — Pluralization (Never Manual)

```typescript
// ✅ i18next handles all plural rules (CLDR-based, covers all languages)
// en/common.json
{
  "items_count": "{{count}} item",
  "items_count_other": "{{count}} items",
  "items_count_zero": "No items"
}
t('common.items_count', { count: 0 })  // "No items"
t('common.items_count', { count: 1 })  // "1 item"
t('common.items_count', { count: 5 })  // "5 items"

// ❌ Never
`${count} ${count === 1 ? 'item' : 'items'}`
// Arabic has 6 plural forms. Russian has 3. This breaks everything.
```

## Rule 5 — Namespace Splitting + Lazy Loading

```typescript
// i18next config — lazy load namespaces
i18next.init({
  ns: ['common'],           // only common loads at startup
  defaultNS: 'common',
  partialBundledLanguages: true,
  backend: {
    loadPath: '/locales/{{lng}}/{{ns}}.json',
  },
})

// Load namespace only when route needs it
// TanStack Router loader:
export const loader = async () => {
  await i18next.loadNamespaces('dashboard')
  return {}
}

// ✅ Result: initial bundle contains ONLY common.json for active locale
// Dashboard strings load with dashboard route
// Auth strings load with auth route
// Zero upfront overhead for unused namespaces
```

**Bundle size rule:** No locale bundle should exceed **50KB**. Run `pnpm i18n:bundle-size` in CI.

## Rule 6 — RTL Support (CSS Logical Properties)

### The Right Approach: Logical Properties
```css
/* ❌ Physical properties — break RTL */
.card { margin-left: 16px; padding-right: 24px; border-left: 2px solid; }

/* ✅ Logical properties — auto-flip with dir="rtl" */
.card { margin-inline-start: 16px; padding-inline-end: 24px; border-inline-start: 2px solid; }
```

### Tailwind — Use RTL Variants
```tsx
// tailwind.config.js — enable RTL plugin
plugins: [require('tailwindcss-rtl')]

// In components — use logical variants
<div className="ms-4 pe-6 border-s-2">  {/* ms/me/ps/pe/bs/be = logical */}
  <ArrowRight className="rtl:rotate-180" />  {/* flip directional icons */}
</div>
```

### Root HTML Pattern
```tsx
// Layout component — set dir + lang at root
export function RootLayout({ locale, children }) {
  const dir = RTL_LOCALES.includes(locale) ? 'rtl' : 'ltr'
  return (
    <html lang={locale} dir={dir}>
      <body className={dir === 'rtl' ? 'font-arabic' : 'font-sans'}>
        {children}
      </body>
    </html>
  )
}

const RTL_LOCALES = ['ar', 'he', 'ur', 'fa', 'yi', 'ku']
```

### RTL-Specific Rules
- **Icons:** Directional icons (arrows, chevrons, back/forward) must rotate 180° in RTL
- **Animations:** Slide-in from left in LTR → slide-in from right in RTL
- **Numbers:** Always LTR even inside RTL text (`dir="ltr"` on number spans)
- **Fonts:** Arabic needs `font-feature-settings: "kern"`. Load Arabic font separately
- **Images:** Decorative layout images (people looking left/right) may need RTL versions
- **Shadows:** `shadow-sm` doesn't flip — verify visually in RTL

## Rule 7 — Locale Detection (Cloudflare-First)

```typescript
// workers/ingest/src/locale.ts
export function detectLocale(request: Request): LocaleResult {
  // 1. User preference (highest priority — explicit choice)
  const stored = getCookie(request, 'user_locale')
  if (stored && SUPPORTED_LOCALES.includes(stored)) {
    return { locale: stored, source: 'preference' }
  }

  // 2. URL prefix (/ar/dashboard, /fr/settings)
  const urlLocale = extractFromUrl(request.url)
  if (urlLocale) return { locale: urlLocale, source: 'url' }

  // 3. Cloudflare headers — free, no IP lookup needed
  const cfLocale = request.headers.get('CF-IPCountry')
  const cfTimezone = (request as any).cf?.timezone
  if (cfLocale) {
    const mapped = COUNTRY_TO_LOCALE[cfLocale]
    if (mapped) return { locale: mapped, source: 'cloudflare', timezone: cfTimezone }
  }

  // 4. Accept-Language header
  const acceptLang = request.headers.get('Accept-Language')
  const parsed = parseAcceptLanguage(acceptLang)
  for (const lang of parsed) {
    if (SUPPORTED_LOCALES.includes(lang)) {
      return { locale: lang, source: 'header' }
    }
  }

  // 5. Default
  return { locale: 'en', source: 'default' }
}
```

**SEO:** Use URL prefix (`/ar/dashboard`) — best for SEO, shareable, crawlable.
**User preference:** Store in DB profile + `user_locale` cookie for edge access.

## Rule 8 — Formatting (Always Intl API)

### Dates
```typescript
// formatter.ts — centralized, never inline
export function formatDate(
  date: Date | string,
  locale: string,
  style: 'short' | 'medium' | 'long' | 'full' = 'medium'
): string {
  return new Intl.DateTimeFormat(locale, {
    dateStyle: style,
  }).format(new Date(date))
}

// Results:
// en-US: "Sep 2, 2026"
// ar:    "٢ سبتمبر ٢٠٢٦"
// ja:    "2026年9月2日"
// de:    "2. Sept. 2026"

// ❌ Never
new Date().toLocaleDateString() // uses browser/server locale, not user locale
date.format('MM/DD/YYYY')       // hardcoded format, wrong for most of the world
```

### Numbers & Currency
```typescript
export function formatCurrency(
  amount: number,   // Always in smallest unit (cents)
  currency: string, // ISO 4217: 'USD', 'EUR', 'INR', 'AED'
  locale: string
): string {
  return new Intl.NumberFormat(locale, {
    style: 'currency',
    currency,
    minimumFractionDigits: ZERO_DECIMAL_CURRENCIES.includes(currency) ? 0 : 2,
  }).format(amount / 100) // convert from cents
}

// Results:
// en-US + USD: "$12.99"
// de + EUR:    "12,99 €"
// ar + SAR:    "١٢٫٩٩ ر.س."
// hi + INR:    "₹12.99"

export function formatNumber(n: number, locale: string): string {
  return new Intl.NumberFormat(locale).format(n)
  // en: "1,234,567"
  // de: "1.234.567"
  // ar: "١٬٢٣٤٬٥٦٧"
}
```

### Units (Metric vs Imperial)
```typescript
export function formatUnit(
  value: number,
  unit: Intl.NumberFormatOptions['unit'],
  locale: string
): string {
  const usesImperial = IMPERIAL_LOCALES.includes(locale) // ['en-US', 'en-GB', 'my', 'lr']
  return new Intl.NumberFormat(locale, {
    style: 'unit',
    unit: usesImperial ? toImperial(unit) : unit,
    unitDisplay: 'short',
  }).format(value)
}
```

## Rule 9 — Locale-Specific UX

| Locale | Date format | Name order | Address format | Notes |
|--------|-------------|------------|----------------|-------|
| en-US | MM/DD/YYYY | First Last | Street, City, ST ZIP | Imperial units |
| en-GB | DD/MM/YYYY | First Last | Street, Town, Postcode | Metric units |
| de | DD.MM.YYYY | Last, First | Street Nr, PLZ City | 24h time default |
| ja | YYYY/MM/DD | Last First | Postal, Prefecture, City, Street | Honorifics required |
| ar | DD/MM/YYYY | (varies) | (varies) | RTL, Islamic calendar option |
| hi | DD/MM/YYYY | First Last | Building, Street, City, PIN | Indian numbering (lakh, crore) |
| zh | YYYY年MM月DD日 | Last First | Province, City, District, Street | No spaces in names |

**Forms must adapt:**
- Name fields: single "Full name" or split First/Last based on locale convention
- Phone: use `react-phone-number-input` with locale-aware country default
- Address: use locale-aware address form (different field order per country)
- Postal codes: validate per country pattern (US: 5 digits, UK: alphanumeric, IN: 6 digits)

## Rule 10 — Translation Workflow (AI-Assisted)

### How translations happen
```
1. Developer writes feature in English (en/ is always canonical)
2. CI runs i18next-cli → detects new/changed keys
3. Claude translates to all supported locales (with cultural context, not literal)
4. Human native speaker reviews for tone/culture (for customer-facing markets)
5. Translation ships with feature — never separately
```

### Claude translation rules
```
When translating for i18n:
- Never translate literally — translate meaning and tone
- Preserve {{interpolation}} variables exactly as-is
- Preserve HTML tags if present
- Match formality level of surrounding strings in that namespace
- For Arabic: use Modern Standard Arabic (MSA) unless regional specified
- For Japanese: use です/ます (polite) form
- For German: use Sie (formal) for B2B, du (informal) for consumer
- For Hindi: use आप (formal) form
- Flag strings with cultural assumptions (idioms, humor, metaphors)
- Note strings that may need locale-specific alternatives (not just translations)
```

## Rule 11 — i18n Testing

```typescript
// 1. Pseudo-locale testing — catches hardcoded strings
// Add to i18next config in dev:
pseudoLocale: 'pseudo', // wraps all translated strings in [[ ]]
// Any string NOT wrapped = hardcoded = bug

// 2. Text expansion test — translations can be 30-200% longer than English
// German is ~30% longer, Finnish can be 100% longer
// Test all layouts with de locale — if it breaks, layout is too tight

// 3. RTL smoke test — all pages with dir="rtl"
// Automated: Playwright test with { locale: 'ar' }

// 4. Missing key detection
test('no missing translation keys', async () => {
  const result = await exec('pnpm i18n:check')
  expect(result.stderr).toBe('')
})

// 5. Type check passes
test('translation types are valid', async () => {
  const result = await exec('tsc --noEmit')
  expect(result.code).toBe(0)
})
```

**CI gates:**
- `pnpm i18n:check` — missing keys → build fails
- `pnpm i18n:bundle-size` — bundle > 50KB → build fails
- RTL Playwright smoke test — any RTL page error → build fails

## Supported Locales — How to Add One

```typescript
// packages/i18n/index.ts
export const SUPPORTED_LOCALES = [
  'en',    // English (default)
  'ar',    // Arabic (RTL)
  'fr',    // French
  'de',    // German
  'hi',    // Hindi
  'ja',    // Japanese
  'zh',    // Chinese (Simplified)
  'es',    // Spanish
] as const

// To add a new locale:
// 1. Add to SUPPORTED_LOCALES
// 2. Create locales/<code>/ directory
// 3. Copy en/ structure, translate all files
// 4. Add to COUNTRY_TO_LOCALE map
// 5. Test with Playwright { locale: '<code>' }
// 6. Add RTL_LOCALES if applicable
```
